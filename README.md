# InvenTree QA Submission

This submission contains quality-engineering instructions, manual test case documents, Playwright API and UI automation, and a location for optional execution evidence.

## Structure

- `agents/` indexes the agent artifacts required by the brief: `agents.md` (custom agent definitions), `prompts.md` (phase prompts and how to run them), and `system-instructions.md` (instruction files). All point to the files in `.github/`.
- `.github/` contains the GitHub Copilot agent configuration:
  - `copilot-instructions.md`: shared scope and rules applied to every request
  - `agents/inventree-quality-engineer.agent.md`: the custom agent used for all phases
  - `instructions/`: file-specific rules for manual test cases and Playwright tests
  - `prompts/`: one prompt per phase, run in order as slash commands: `/ui-manual-tests`, `/api-manual-tests`, `/api-automation`, `/ui-automation`, `/review-and-correct`
- `test-cases/` contains the manual test cases. `ui-manual-tests.md` and `api-manual-tests.md` are index pages with coverage summaries; the cases are in one file per feature area under `test-cases/ui/` and `test-cases/api/`. `api-automation-tests.md` and `ui-automation-tests.md` give the run order for the automation phases.
- `automation/api/` contains authenticated API checks. See its README for setup and commands.
- `automation/ui/` contains browser-based checks with a one-time login setup.
- `automation/shared/` contains TypeScript source used by both projects (API token handling, part and category API services, models, test-name helper, cleanup annotations, redaction patterns). It has no `package.json`; each project compiles it with its own dependencies, so the two projects stay separate npm packages.
- `video/` holds [video-link.txt](video/video-link.txt), the link to the demo recording ([Google Drive](https://drive.google.com/file/d/12mvu2Ke2l37gLew5iqu-ywI1ojrl-Q2h/view?usp=sharing), about 45 minutes, 1080p MP4, 695 MB). Google Drive may show a virus-scan warning because of the file size; choose *Download anyway*.

## Setup

The API and UI projects are independent npm packages. In each project directory, run `npm ci`. Configure `automation/api/.env` from `.env.example` for API tests. Set `ENV=LOCALHOST` (default, `http://localhost`) or `ENV=REMOTE` (`https://demo.inventree.org`); the URL mapping is in `automation/shared/environments.ts`.

Run the API checks with `npm run test:api` and the UI checks with `npm run test:ui`, each from its corresponding project directory. Install the Playwright Chromium browser for UI checks with `npx playwright install chromium`. Run only the smoke set with `npx playwright test --grep @smoke`.

Parallelism and retries are set per run with environment variables (also the CI build parameters): `WORKERS` (a number such as `4`, or a percentage such as `50%`; default `2` in both projects, locally and on CI) and `RETRIES` (default `2`, locally and on CI). On local 1.6.3, more than one worker can corrupt the category tree (API) and log browsers out (UI), see *Open Review Findings*; use `WORKERS=1` if that happens. Tests that pass only on retry are reported as `flaky`. An invalid value stops the run. For example, in PowerShell: `$env:WORKERS='4'; $env:RETRIES='1'; npm run test:api`.

Reports: Playwright HTML (`npm run report`) and Allure (`npm run allure:generate`, then `npm run allure:open`, which serves it on `127.0.0.1`). `allurerc.mjs` builds a single self-contained `index.html`, so a downloaded CI artifact also opens directly from disk. Test history (History tab, trends, flaky detection) is kept in `allure-history/history.jsonl` (last 20 runs, git-ignored). On CI, the workflow restores it from the Actions cache before generating and saves it afterwards, with a separate history per project, environment, and run type (`nightly`, `manual`, `smoke`). GitHub can evict an unused cache after 7 days, which starts the history again. The UI project keeps a screenshot and a video of each failed test (`screenshot: 'only-on-failure'`, `video: 'retain-on-failure'`), and both reports include them with the redacted trace. Videos cannot be redacted like traces; they are safe because tests log in through the API and never type a password in the browser. API tests have no browser, so they produce no screenshots or videos.

## Continuous Integration

[.github/workflows/playwright.yml](.github/workflows/playwright.yml) runs the API and UI projects in parallel jobs (typecheck, spec layering check, then tests). `npm run lint:specs` (run from each project) fails the build when a spec calls `page.*` or the HTTP client directly, asks for a raw request fixture, sleeps with `waitForTimeout`, or commits `.only`; the rules are in `automation/shared/check-spec-layering.mjs`.

| Trigger | Tests run | Environment |
|---|---|---|
| Pull request to `main` that changes `automation/**` | `@smoke` | `LOCALHOST` |
| Push (merge) to `main` that changes `automation/**` | `@smoke` | `LOCALHOST` |
| Nightly schedule (`0 2 * * *` UTC, default branch) | Everything (no `--grep`), split over 4 shards, 120-minute timeout | `LOCALHOST` |
| Manual (*Actions > Playwright automation > Run workflow*) | `tags` input as a `--grep` filter (defaults to `@smoke`; `.` runs everything) | `environment` input: `LOCALHOST` (default) or `REMOTE` |

Every run uses `LOCALHOST` unless a manual run selects `REMOTE`, because the public demo is sometimes down. Before selecting `REMOTE`, open [https://demo.inventree.org/web/login](https://demo.inventree.org/web/login) and check that the login page loads; the job also checks this first and stops with a message to re-run on `LOCALHOST` if the site does not answer. With `LOCALHOST`, each job runs [.github/scripts/start-local-inventree.sh](.github/scripts/start-local-inventree.sh), which downloads InvenTree's own docker compose recipe for the pinned version (`INVENTREE_VERSION`, `1.6.3`, the same as the local reference instance), generates a superuser and database password for that run (masked in logs), runs `invoke update`, starts the stack on `http://localhost`, waits until `GET /api/user/me/` answers, and sets `PART_ENABLE_LOCKING`, `PART_ALLOW_DUPLICATE_IPN`, and `PART_CREATE_INITIAL` to the reference instance's values. The tests then run against `http://localhost` exactly as locally. The script also creates a view-only `READER` user through the REST API (a group with view-only access to every area except admin, then the user and its password), so `READER` tests run too. The instance is discarded with the runner. If a run fails, the job prints the last 200 lines of the server log.

Build parameters (manual runs):

| Parameter | Values |
|---|---|
| `environment` | `LOCALHOST` (default): a throwaway InvenTree started inside each job; needs no secrets. `REMOTE`: the demo site, with the `REMOTE` environment secrets; check [the login page](https://demo.inventree.org/web/login) loads before choosing it |
| `tags` | Playwright `--grep` filter. Defaults to `@smoke`; use `.` to run everything. Cleared to empty, it runs `@smoke`, or the whole suite when `shards` is more than 1 |
| `workers` | Parallel workers, passed as `WORKERS`: a number or percentage (`50%`). Empty uses `2`. On `LOCALHOST`, set `1` if category tests fail: parallel category writes can corrupt the category tree (see *Open Review Findings*) |
| `retries` | Retries per failed test, passed as `RETRIES`. Empty uses `2`. Tests that pass only on retry are marked `flaky` in both reports |
| `shards` | Number of parallel runners per project, 1 to 8 (empty or `1` runs everything in one job). A small `plan` job turns it into a matrix, and shard `N` of `total` runs Playwright `--shard N/total`. With `tags` set to `.` and `shards` above 1, the shards cover the whole suite; the default `@smoke` filter would leave only a handful of tests to split |

**Scaling.** Pull requests stay fast with `@smoke`; the nightly run is the regression gate. When the suite outgrows one job, raise `shards`: the workflow fans out one job per project and shard (4 shards means 8 jobs), each with its own `blob-report-<project>-shard-<n>` and `allure-results-<project>-shard-<n>` artifacts (kept 1 day). A `merge-reports` job per project then combines all shards, even when some failed, into one `playwright-report-<project>` (`npx playwright merge-reports`) and one `allure-report-<project>` (kept 14 days). Every test owns its data, so shards do not share state. The remaining shared state is the target instance (its global settings and one superuser), so raising `WORKERS` is limited by that instance, not by the framework: the local Docker server drops requests under parallel UI load (see `automation/ui/README.md`), and parallel API runs can corrupt the category tree (see *Open Review Findings*, category tree race condition), so local runs are reliable only with `WORKERS=1`.

**Roles are chosen in code, not in the pipeline,** so one build can run tests as several users. A test passes its role (`SUPERUSER` by default, or `READER`) with `test.use({ role: 'READER' })`, and `automation/shared/roles.ts` reads `<ROLE>_USERNAME` / `<ROLE>_PASSWORD` (for example `SUPERUSER_USERNAME`, `READER_USERNAME`). In the API project the role applies to every request in that block; in the UI project it selects the browser login (one storage state per role, saved by `auth.setup.ts`), while API setup and cleanup stay on the superuser. Tests for a role with no credentials in the current environment are skipped with a reason. Each login is checked against `GET /api/user/me/`: `SUPERUSER` must be a superuser, and `READER` must be a non-staff, non-superuser account. `LOCALHOST` has only the superuser, so leave the reader variables empty there. Trace redaction covers every configured password.

Create a `REMOTE` GitHub environment (*Settings > Environments*) with these secrets. Never commit the values. `LOCALHOST` runs need no secrets: GitHub creates an empty `LOCALHOST` environment on the first run, and the credentials are generated inside the job.

| Environment | Secrets |
|---|---|
| `REMOTE` | `SUPERUSER_USERNAME`, `SUPERUSER_PASSWORD`, `READER_USERNAME`, `READER_PASSWORD` |

On `REMOTE` the superuser secrets are required; the job fails before tests run without them. The public demo may run a newer version than local 1.6.3 / API 561. Pull requests from forks receive no secrets. Reports and redacted traces are uploaded as one merged report per project: `playwright-report-api` and `playwright-report-ui`, and the Allure reports as `allure-report-api` and `allure-report-ui`. On CI, only sharded runs (`shards` above 1) write `blob` reports and merge them; a single-job run and local runs write `playwright-report/` directly.

Smoke set: API-PART-001, API-PART-005, API-CAT-001, API-CAT-003, SMOKE-001, SMOKE-002, UI-CREATE-001 (the UI login setup always runs).

## Tool Choices and Approach

Playwright Test with TypeScript is used for both automation projects. API authentication is provided by the shared worker-scoped fixture in `automation/api/tests/fixtures.ts`; tests must not duplicate credential or token handling. UI checks use accessible browser-level behavior and explicit assertions. Manual cases must be grounded in the InvenTree schema and documentation referenced by the prompt, with unsupported details recorded as open questions.

Credentials and tokens belong only in ignored local environment files. Do not put secrets in test cases, reports, prompts, screenshots, or recordings.
